# Finder стендов Giga Cowork

**Версия: v4.0.21**

Скрипт для поиска стендов (`config.yaml`) в Git-репозитории `argocd` по `cowork_subdomain`, `admin_email`, `ИНН` или `stand_name`. Скрипт автоматически обновляет репозиторий, рекурсивно ищет конфиги в заданных зонах и выводит информацию о найденных стендах, а также предоставляет быстрый доступ к связанным инструментам и **управление пространствами** (смена владельца, добавление пользователей, вывод списка пространств).

**Репозиторий:**
[https://git.sberdevices.ru/gigabb/sdb_support/finder](https://git.sberdevices.ru/gigabb/sdb_support/finder)
Клонирование: `git clone git@git.sberdevices.ru:gigabb/sdb_support/finder.git` или `https://git.sberdevices.ru/gigabb/sdb_support/finder.git`

---

## Возможности

- **Поиск стендов** по одному или нескольким критериям:
  - `cowork_subdomain`
  - `admin_email`
  - `ИНН`
  - `stand_name`
- **Вывод полной информации** о найденных стендах (папка, зона, `stand_name`, `cowork_subdomain`, `admin_email`, ИНН, `expiry_date`, `cowork_revision`, признак `[broken stand]`).
- **Интерактивное меню** после выбора стенда:
  1. Открыть Admin Helper и ArgoCD
  2. Зайти на тенант (`https://<subdomain>.cowork.ru`)
  3. Открыть консоль тенантов (`https://tenant-console.cowork.ru/`)
  4. Запустить FAQ-агента (открывает страницу агента)
  5. Открыть конфигурацию стенда (страница кластера в GitLab)
  6. Управление пространствами
  7. Починить роли на стенде
  8. Токены LLM (ClickHouse)
  9. Создать аккаунты (Excel с email/password)
  0. Вернуться к поиску
- **Управление пространствами** (пункт 6, подменю):
  1. Сменить владельца пространства — генерирует `change_workspace_owner.py` (DRY RUN → APPLY)
  2. Добавить пользователя в пространство — генерирует `add_user_to_workspace.py` (DRY RUN → APPLY; можно указать несколько email через запятую; для отсутствующих в users выводится статус приглашения из `invite_tokens`)
  3. Массовое добавление в пространство — генерирует `add_all_users_to_workspace.py` (без dry run, с подтверждением)
  4. Показать все пространства на стенде — генерирует `list_workspaces.py` (только чтение)
  5. Добавить базовые пространства — генерирует `add_user_to_base_workspaces.py` (DRY RUN → APPLY; пункт виден только на стенде demo, нужен только email, можно несколько через запятую; для отсутствующих в users выводится статус приглашения из `invite_tokens`)
  6. Удалить пользователя из пространства — генерирует `remove_user_from_workspace.py` (DRY RUN → APPLY; можно указать несколько email через запятую; находит все user_id по email — yggdrasil + heimdall_auth, ловит legacy-гранты «пересозданных» пользователей; владелец пространства не удаляется — сначала смените владельца; идемпотентен)
- **Токены LLM (ClickHouse)** (пункт 8): сводка по потреблению токенов на стенде напрямую из ClickHouse Langfuse (таблица `default.observations`) — «Потрачено за период: N токенов», «запрос к модели (input)» / «ответ модели (output)» отдельно, число вызовов. Finder сам открывает веб-терминал пода `chi-langfuse-default-0-0-0` (приложение `langfuse`, один на все зоны) и выводит готовую команду `clickhouse-client --query "…"` для выполнения там; результат вставляется в finder. Ключи Langfuse не нужны. Только чтение, ничего не меняет.
- **Создание аккаунтов** (пункт 9): массовое создание пользователей на стенде через `auth_sdk` в поде heimdall-auth. Вводятся логины через запятую (логин = часть до @, FIO подставляется из логина автоматически), домен берётся из `admin_email` результата поиска (можно переопределить). Finder генерирует команду heredoc `/app/services/auth/.venv/bin/python <<'PY' … PY` (сохраняет в `exec/create_accounts_<stand>.sh`), пользователь запускает её в веб-терминале пода heimdall-auth*, а вывод скрипта вставляет обратно в finder — он распознаёт пары email/password и формирует Excel-файл `accounts_<stand>_<дата_время>.xlsx` со столбцами `email` и `password`.
- **Фоновая проверка изменений в репозитории**: раз в 15 минут finder тихо выполняет `git fetch` и сравнивает локальный HEAD с origin/<ветка>. Если появились новые коммиты, при следующем простое (перед экраном критериев поиска) выводится уведомление «Найдены изменения в конфигурациях стендов (N)», где N — количество новых коммитов (жёлтым). Если накопилось больше 10 коммитов, проверка ускоряется до 30 секунд, чтобы счётчик не «зависал» на старом значении до конца 15-минутного интервала и вопрос «Обновить локальный репозиторий? (yes/no)». Во время работы в меню уведомления не показываются. Ответ «no» не дёргает повторно за то же состояние — спросим снова только когда на origin появится новый коммит. При «yes» выполняется pull, отчёт об изменениях (папка news/), пересборка зон; ошибка обновления не прерывает сессию.
- **Автоопределение зоны** (st02 / tb01 / tb04) из результата поиска стенда — ручной выбор не нужен.
- **Полуавтоматический ввод URL баз данных**: finder сам открывает страницу приложения yggdrasil / heimdall в ArgoCD, пользователь копирует строку из `env | grep ...` в поде и вставляет в finder целиком (в формате `ИМЯ_ПЕРЕМЕННОЙ=postgresql://...`). Введённые DSN кэшируются по стендам (`~/.gigafinder/dsn-cache.json`) — при следующем запуске для того же стенда вводить не придётся (Enter — из кэша, `d` — заново).
- **Автодополнение DNS-суффикса**: короткое имя хоста из пода (`yggdrasil-postgres-rw`) автоматически дополняется до `yggdrasil-postgres-rw.<stand_name>.svc.cluster.local`.
- Автоматическое обновление локального репозитория `argocd` перед поиском.
- Сохранение изменений, появившихся в репозитории после последнего обновления, в папку `news/` (для аудита).
- Автоматическое обнаружение новых кластеров в репозитории и предложение добавить их в конфигурацию.

## Требования

- Python 3.6+ (для запуска `finder-pro.py` локально).
  Сгенерированные скрипты используют синтаксис Python 3.10+ и запускаются в поде debug-ubuntu, где Python достаточно новый.
- Git (установлен и настроен).
- Доступ к репозиторию `git@git.sberdevices.ru:gigabb/infra/cowork/argocd.git` (SSH или HTTPS) — **этот репозиторий остаётся корпоративным** и используется скриптом для поиска стендов.
- Локальная папка `~/Documents/Giga/cowork/argocd` (по умолчанию) или измените путь в переменной `REPO_PATH` в скрипте. Если репозиторий лежит в нестандартном месте — finder попросит указать путь один раз и запомнит его в `repo_local_path.txt` рядом со скриптом (v2.7.10).
- Браузер (finder открывает страницы ArgoCD и тенантов через `webbrowser`).
- Доступ к ArgoCD зоны (`https://argocd-st02.cowork.ru`, `https://argocd-tb01.cowork.ru`, `https://argocd.cowork.gigab2b.ru`, `https://argocd-tb04.cowork.ru`) — для подменю «Управление пространствами».

## Использование

Запустите скрипт:

```bash
python3 finder-pro.py
```

или, если создан алиас, просто `finder`.

При старте среда запуска определяется автоматически: **Windows** и **macOS** — без вопроса (нативный режим, браузер через `webbrowser`). На **Linux** скрипт спросит: **1 — Нативный Linux**, **2 — WSL**.
- **Нативный (Windows / macOS / Linux)**: браузер и файлы открываются штатно (`webbrowser`).
- **WSL**: URL и локальные файлы открываются в Windows-браузере через `cmd.exe /c start`, пути переводятся через `wslpath -w` (нужен WSL с доступом к Windows-подсистеме).

## Алгоритм работы

1. **Обновление репозитория `argocd`**: выполняется `git fetch` и `git pull origin <ветка>`, сразу выводится URL удалённого репозитория. Перед обновлением finder проверяет рабочее дерево: если файлы репозитория удалены вручную (например, содержимое папки перенесли в другое место) — они автоматически восстанавливаются из последнего коммита (`v2.7.12`), изменённые файлы не затрагиваются. Отчёт об изменениях выводится после самопроверки зон: сначала список изменённых файлов с их `cowork_subdomain`, потом — путь к файлу с полным diff в папке `news/`.

2. **Конфигурация зон**: файл `zones/zones_config.json` создаётся автоматически при первом запуске (папка `zones/` тоже создаётся сама). При каждом запуске скрипт сверяет список кластеров с репозиторием: исчезнувшие кластеры помечаются ошибкой, новые — предлагаются к добавлению.
3. **Самопроверка доступности зон**: для каждой зоны проверяется, что папка существует, читаема и содержит `config.yaml`. Выводится `[OK] <зона>: N конфиг(ов)` (зелёный); зона без конфигов — `[ПРЕДУПРЕЖДЕНИЕ]` (жёлтый, поиск по ней вернёт пусто); папка не найдена или не читается — `[ERROR]` (красный) и остановка запуска.

4. **Запрос критериев поиска**: введите значения для полей (можно оставить пустыми, но хотя бы одно должно быть заполнено): `cowork_subdomain`, `email`, `ИНН`, `stand_name`.

5. **Поиск**: скрипт рекурсивно обходит зоны (st02, tb01, tb04) в поисках файлов `config.yaml` внутри папок, начинающихся с `cowork-`. Для каждого найденного конфига извлекаются все необходимые поля. Сравнение с критериями происходит без учёта регистра (кроме ИНН).

6. **Вывод результатов**: список всех подходящих стендов с подробной информацией. Если найден только один стенд, он выбирается автоматически; если несколько — предлагается выбрать номер.

7. **Меню действий для выбранного стенда**:

   ```
   [ACTION] Выбрать действие
     1. Открыть Admin Helper и ArgoCD
     2. Зайти на тенант
     3. Открыть консоль тенантов
     4. Запустить FAQ-агента
     5. Открыть конфигурацию стенда
     6. Управление пространствами
     7. Починить роли на стенде
     8. Токены LLM (ClickHouse)
     9. Создать аккаунты (Excel с email/password)
     0. Вернуться к поиску
   ```

   При выборе любого пункта (кроме 0) соответствующая страница открывается в браузере, после чего меню снова отображается — можно выполнить несколько действий подряд. Выбор 0 возвращает к вводу критериев поиска.

## Управление пространствами (пункт 6)

Подменю:

```
[ACTION] Управление пространствами
  1. Сменить владельца пространства
  2. Добавить пользователя в пространство
  3. Массовое добавление в пространство
  4. Показать все пространства на стенде
  5. Добавить базовые пространства  # только для стенда demo
  6. Удалить пользователя из пространства
  0. Назад
```

Зона (st02 / tb01 / tb04) определяется автоматически из расположения найденного стенда — выбирать её вручную не нужно.

### Общий порядок работы

1. Finder запрашивает параметры функции (ID пространств, email — в зависимости от пункта).
2. Finder открывает в браузере страницу приложения **yggdrasil** (и **heimdall**, если функция работает с Heimdall) в ArgoCD нужной зоны. В списке приложения выбираете под `yggdrasil*` (или `heimdall*`), открываете вкладку **exec** и выполняете:
   - `env | grep YGGDRASIL_DATABASE_URL` (для yggdrasil);
   - `env | grep AUTH_DATABASE_URL` (для heimdall).
   Если DSN для этого стенда уже вводились ранее, finder предложит взять их из кэша (Enter) или ввести заново (`d`) — шаг 2–3 можно пропустить.
3. Копируете результат **целиком** (строку вида `ИМЯ_ПЕРЕМЕННОЙ=postgresql://...`) и вставляете в finder. Finder сам отбрасывает префикс переменной и дополняет хост полным DNS-суффиксом неймспейса стенда.
4. Finder сохраняет готовый скрипт в папку `exec/` (создаётся автоматически) и открывает страницу приложения `cowork/cowork` в ArgoCD.
5. В списке приложения выбираете под `debug-ubuntu*`, открываете вкладку **exec**, копируете содержимое сгенерированного скрипта в веб-терминал и запускаете: `python3 <имя_скрипта>.py`.

### Пункт 8. Токены LLM (ClickHouse)

Сводка по потреблению токенов на стенде напрямую из ClickHouse Langfuse (таблица `default.observations`): «Потрачено за период», «запрос к модели (input)» / «ответ модели (output)» отдельно, число вызовов. Только чтение, ничего не меняет. Ключи Langfuse не нужны.

Порядок работы:

1. Интерактивный выбор периода: 7 дней / 30 дней / свой (число дней).
2. Finder сам открывает веб-терминал пода `chi-langfuse-default-0-0-0` (приложение `langfuse`) — ClickHouse один на все зоны, поэтому ссылка всегда одна: `https://argocd-tb01.cowork.ru/applications/langfuse/langfuse?view=tree&node=%2FPod%2Flangfuse%2Fchi-langfuse-default-0-0-0&tab=exec&resource=`.
3. Выводится готовая команда `clickhouse-client --query "…"` с SQL (`environment = '<stand_name>'`, `type = 'GENERATION'`, период, группировка по `provided_model_name` + input/output/total из `usage_details`) — выполняется прямо в открытом веб-терминале пода; результат (все строки, TabSeparated или пробелы) вставляется в finder целиком — многострочная вставка (несколько моделей) читается полностью.
4. Сводка (с подсветкой `[INFO]`): «Токены LLM за последние N дн.», «Потрачено за период: N токенов», «запрос к модели (input)» / «ответ модели (output)» отдельно, число вызовов. NULL (`\N`) обрабатывается; если `total` пустой — считается как `input + output`. Парсер принимает и табы, и пробелы (копирование из веб-терминала ArgoCD превращает табы в пробелы).

Типовые проблемы:

- `Unknown expression identifier/function '…'` — устаревшие имена колонок из API (camelCase); в таблице `default.observations` всё snake_case: `provided_model_name`, `start_time`.
- Пустой результат (ClickHouse ничего не вернул) — скрипт выводит «Данных нет: за последние N дн. на стенде <stand_name> (<subdomain>) не найдено вызовов LLM»: возможно, за период не было вызовов LLM или `environment` отличается от `stand_name`.

### Пункт 9. Создать аккаунты (Excel с email/password)

Массовое создание пользователей на стенде через `auth_sdk` в поде heimdall-auth.

Порядок работы:

1. Ввод логинов через запятую. Логин — часть до @ (например, `user81` из `user81@21-school.ru`); если указан полный email, часть после @ отбрасывается. FIO подставляется из логина автоматически (логин = фамилия, при нескольких словах — остальное = имя).
2. Домен для email определяется из `admin_email` результата поиска (например, `s.sverdlova@21-school.ru` → `21-school.ru`); Enter — принять, либо ввести свой.
3. Finder открывает приложение heimdall в ArgoCD и сохраняет готовую команду heredoc в `exec/create_accounts_<stand>.sh`: `/app/services/auth/.venv/bin/python <<'PY' … PY`. Скрипт внутри: `find_user_by_email` → при отсутствии `create_provider_user`, затем `reset_user_password` со сгенерированным паролем (24 символа, буквы/цифры/спецсимволы). Для каждого пользователя печатает `email:` / `password:` / `user_id:`, в конце — строку ИТОГО.
4. Пользователь копирует содержимое `.sh` целиком в веб-терминал пода heimdall-auth* и запускает.
5. Вывод скрипта вставляется обратно в finder — он распознаёт пары email/password (ANSI-коды отбрасываются) и формирует Excel-файл `accounts/accounts_<stand>_<дата_время>.xlsx` со столбцами `email` и `password` (папка `accounts/` создаётся автоматически при первом сохранении; запись — только stdlib: zip + XML, без openpyxl).

## Примечания

- Finder не изменяет файлы конфигурации `argocd` — только читает их.
- Кэш DSN хранится в `~/.gigafinder/dsn-cache.json` (вне папки finder). Файл содержит пароли БД — не коммитьте и не пересылайте его.
- Все изменения в репозитории `argocd`, появившиеся после последнего pull, сохраняются в папку `news/` для отслеживания.
- Для работы репозиторий `argocd` должен быть клонирован; если его нет — finder предложит указать путь к существующему или склонировать сам (v2.7.10). Введённый вручную путь запоминается в `repo_local_path.txt` рядом со скриптом (персональный файл — не коммитьте его, у каждого свой путь).
- Если зоны (cce-prod-st02, cce-prod-tb01, cce-sdb-tb01-stands, cce-prod-tb04) не найдены, скрипт завершится с ошибкой.
- Меню действий остаётся активным после каждого выбора, позволяя выполнить несколько действий без повторного поиска.
- **Безопасность**: сгенерированные скрипты в `exec/` содержат пароли БД в открытом виде. Не коммитьте их в репозиторий и удаляйте из пода после прогона (`rm <имя_скрипта>.py`).
- Сгенерированные скрипты идемпотентны: повторный запуск безопасен, существующие записи не меняются.
- Изменения в Yggdrasil и Heimdall выполняются в транзакциях; если вторая БД не даст commit — первая откатится. При сбое между транзакциями достаточно перезапустить скрипт.

## Версионирование

Схема semver `MAJOR.MINOR.PATCH`:

- **MAJOR** — ломающие изменения: смена структуры меню, несовместимость кэшей/конфигов, перестройка архитектуры.
- **MINOR** — новые функции и возможности (новый пункт меню, новый режим, новая интеграция).
- **PATCH** — исправления багов, улучшения существующего функционала без изменения поведения.

Правило: каждое изменение кода сопровождается bump версии в `VERSION` и записью в «Историю версий» в том же ходе.
